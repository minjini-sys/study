# AWS Lambda MicroVM으로 AI 에이전트 샌드박스 구축하기

- 정리 날짜: 2026-09-19
- 원문 게시일: 2026-09-18
- 공식 출처: [AWS Compute Blog - Running self-hosted AI agent sandboxes with AWS Lambda MicroVMs](https://aws.amazon.com/blogs/compute/running-self-hosted-ai-agent-sandboxes-with-aws-lambda-microvms/)

## 핵심 내용

AWS는 AI 에이전트가 도구를 실행할 때 사용할 수 있는 격리된 샌드박스를 AWS Lambda MicroVM으로 구축하는 방법을 소개했다. 핵심은 각 에이전트 세션마다 새로운 MicroVM을 실행해 코드와 도구 호출을 다른 세션 및 호스트 환경과 분리하는 것이다.

이 구조에서는 제어 영역을 사용자의 AWS 계정 안에 직접 구성할 수 있다. 따라서 자격 증명, 네트워크 경로, 실행 정책, 로깅 및 거버넌스를 조직의 보안 요구사항에 맞게 관리할 수 있다.

## 왜 중요한가

AI 에이전트는 단순히 답변만 생성하는 것이 아니라 셸 명령 실행, 파일 처리, 외부 API 호출처럼 실제 시스템에 영향을 주는 작업을 수행할 수 있다. 여러 사용자의 에이전트 작업을 같은 실행 환경에서 처리하면 데이터 노출, 자격 증명 탈취, 세션 간 간섭 위험이 커진다.

세션마다 별도의 MicroVM을 사용하면 실행 경계를 명확히 만들 수 있다. 특히 민감한 데이터나 내부 도구를 다루는 기업 환경에서는 에이전트의 편의성뿐 아니라 격리, 감사 가능성, 종료 후 정리 과정까지 함께 설계해야 한다.

## 서비스 및 아키텍처 관점

전체 구조는 크게 제어 영역과 실행 영역으로 나눌 수 있다.

1. 제어 영역이 에이전트의 실행 요청을 받는다.
2. 요청마다 격리된 Lambda MicroVM 기반 환경을 준비한다.
3. 필요한 권한과 네트워크 정책을 해당 세션에만 적용한다.
4. 에이전트가 샌드박스 안에서 도구를 실행한다.
5. 실행 결과와 로그를 수집한 뒤 세션 환경을 종료한다.

이 패턴의 장점은 세션별 격리와 AWS 계정 내부 통제다. 반면 실행 환경 준비 시간, 동시 실행 수, 비용, 이미지 및 의존성 관리 방식은 실제 워크로드에 맞게 검토해야 한다.

## 보안 및 운영 관점

- IAM 역할은 에이전트가 실제로 필요한 작업만 수행하도록 최소 권한으로 구성한다.
- VPC와 보안 그룹을 이용해 샌드박스가 접근할 수 있는 내부 자원과 외부 네트워크를 제한한다.
- 세션마다 임시 자격 증명을 사용하고 장기 액세스 키를 실행 환경에 저장하지 않는다.
- 실행 명령, API 호출, 실패 원인과 종료 상태를 중앙 로그에 남겨 감사 가능성을 확보한다.
- 세션 종료 시 임시 파일과 민감 데이터를 확실히 제거한다.
- 동시 실행 한도와 타임아웃을 설정해 무한 실행이나 과도한 비용 발생을 방지한다.

## 시험 및 학습 관점

이번 사례는 특정 기능 암기보다 AWS 보안 설계 원칙과 연결해서 보는 것이 중요하다.

- 최소 권한 원칙과 임시 자격 증명
- 워크로드 및 테넌트 간 격리
- VPC를 이용한 네트워크 경계 설정
- CloudWatch와 CloudTrail을 활용한 관측 및 감사
- 자동 확장 환경에서의 비용과 서비스 할당량 관리
- 생성형 AI 시스템의 도구 실행 보안

## 같이 보면 좋은 학습 포인트

- IAM 역할과 AWS STS 임시 자격 증명

- Amazon Bedrock AgentCore와 자체 구축 샌드박스의 역할 비교
- 에이전트의 프롬프트 인젝션이 도구 실행 권한에 미치는 영향

## 한 줄 정리

AI 에이전트가 실제 도구를 안전하게 실행하려면 세션별 MicroVM 격리와 최소 권한, 네트워크 통제, 감사 로그를 하나의 운영 구조로 설계해야 한다.
