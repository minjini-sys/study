# AWS Step Functions 워크플로, AI 에이전트 도구로 사용 가능

## 공식 출처

- [AWS Step Functions workflows now available as AI agent tools](https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/)
- 발표일: 2026년 10월 29일

## 핵심 내용

AWS Step Functions 워크플로를 Amazon Bedrock AgentCore Gateway를 통해 AI 에이전트의 도구로 사용할 수 있게 되었다.

에이전트는 사용자의 요청과 현재 상황을 바탕으로 워크플로를 언제 실행할지 결정하고 입력값을 전달한다. 실제 다단계 업무 절차는 Step Functions가 미리 정의된 순서와 상태 전이에 따라 실행한다.

이번 기능은 기존 Step Functions의 다음 두 워크플로 유형을 모두 지원한다.

- Standard Workflows
- Express Workflows

AgentCore Gateway는 Model Context Protocol(MCP)을 통해 AI 에이전트와 도구를 연결한다. Step Functions는 220개가 넘는 AWS 서비스의 작업을 오케스트레이션할 수 있으므로, 기존 자동화 자산을 에이전트가 호출 가능한 업무 도구로 확장할 수 있다.

## 왜 중요한가

AI 에이전트는 자연어 요청을 이해하고 상황에 맞춰 행동을 선택하는 데 강점이 있지만, 중요한 업무 절차까지 모델의 즉흥적인 판단에만 맡기면 실행 순서 누락, 중복 호출, 정책 우회 같은 위험이 생길 수 있다.

Step Functions를 에이전트 도구로 사용하면 역할을 다음처럼 분리할 수 있다.

- 에이전트: 사용자의 의도를 이해하고 적절한 워크플로와 입력을 선택
- AgentCore Gateway: 에이전트와 도구 사이의 연결 제공
- Step Functions: 사전에 정의된 순서, 분기, 재시도, 오류 처리에 따라 업무 실행

예를 들어 고객 지원 에이전트가 환불 요청을 판단해 환불 워크플로를 시작하면, Step Functions는 자격 확인, 관리자 승인, 환불 처리 단계를 정해진 정책대로 실행할 수 있다. 에이전트가 각 단계를 임의로 구성하는 대신 검토된 워크플로를 재사용하므로 일관성과 통제력을 높일 수 있다.

## 서비스 및 아키텍처 관점

기본적인 호출 흐름은 다음과 같다.

1. 사용자가 AI 에이전트에 업무를 요청한다.
2. 에이전트가 요청의 의도와 필요한 입력을 분석한다.
3. AgentCore Gateway에 등록된 Step Functions 도구를 선택한다.
4. 에이전트가 워크플로 실행에 필요한 입력을 전달한다.
5. Step Functions가 정의된 상태 머신에 따라 각 단계를 실행한다.
6. 에이전트가 워크플로 실행 상태 또는 결과를 조회해 사용자에게 전달한다.

이 구조에서는 자연어 기반의 유연한 인터페이스와 결정적인 워크플로 실행을 분리할 수 있다. 기존에 운영 중인 상태 머신을 다시 작성하지 않고 에이전트 도구로 노출할 수 있다는 점도 중요하다.

워크플로 유형은 업무 특성에 맞게 선택해야 한다.

- Standard Workflows: 장시간 실행, 정확히 한 번 실행되는 워크플로 실행 의미 체계, 실행 기록과 감사가 중요한 업무에 적합
- Express Workflows: 짧고 호출 빈도가 높은 이벤트 처리에 적합하며 동기식 또는 비동기식 실행 방식을 선택 가능

에이전트가 실행 결과를 기다려야 하는지, 비동기 작업을 시작한 뒤 상태만 조회할지에 따라 인터페이스도 달라진다. 장시간 업무는 실행 ARN을 반환하고 별도로 상태를 조회하는 방식이 적합할 수 있다.

## 보안 관점

에이전트가 워크플로를 호출할 수 있다는 것은 실제 AWS 리소스와 업무 데이터에 영향을 줄 수 있다는 뜻이다. 도구 연결 자체보다 어떤 상태 머신을 어떤 입력으로 실행할 수 있는지 통제하는 것이 핵심이다.

- AgentCore Gateway와 Step Functions 실행 역할에 최소 권한을 적용한다.
- 에이전트별로 호출 가능한 상태 머신과 조회 작업을 제한한다.
- JSON Schema와 애플리케이션 검증을 이용해 입력 형식과 허용값을 검사한다.
- 금액 지급, 권한 변경, 삭제처럼 영향이 큰 단계에는 사람의 승인을 포함한다.
- 사용자 입력이 IAM 리소스 ARN이나 실행 대상에 직접 반영되지 않도록 허용 목록을 사용한다.
- CloudTrail과 Step Functions 실행 기록으로 누가 어떤 워크플로를 호출했는지 추적한다.
- 입력과 출력에 비밀정보나 개인정보가 불필요하게 기록되지 않도록 로깅 정책을 설계한다.

프롬프트 인젝션에 의해 에이전트가 의도하지 않은 도구를 호출할 가능성도 고려해야 한다. 에이전트의 판단만 신뢰하지 말고 권한, 입력 검증, 승인, 워크플로 내부 정책 검사를 여러 계층으로 적용해야 한다.

## 운영 관점

에이전트와 워크플로를 연결하면 모델 호출, Gateway 호출, 상태 머신 실행, 개별 서비스 작업까지 관측 범위가 넓어진다. 장애 지점을 빠르게 찾으려면 각 계층의 상관관계를 추적할 수 있어야 한다.

운영 시에는 다음 항목을 확인한다.

- 에이전트가 선택한 도구와 전달한 입력
- 상태 머신 실행 성공률과 실패한 상태
- 재시도, 타임아웃, 보상 작업 처리
- Standard 및 Express 워크플로의 실행 방식과 비용
- 중복 요청이 업무에 미치는 영향과 멱등성 처리
- 장시간 실행의 상태 조회와 사용자 알림 방식
- AgentCore Gateway 및 Step Functions의 리전 가용성
- 두 서비스의 표준 사용 요금

AWS 공식 발표의 운영 에이전트 예시처럼 워크플로 실행을 조회하면 야간에 실패한 주문과 실패 지점을 빠르게 찾을 수 있다. Amazon CloudWatch 지표와 로그, Step Functions 실행 기록을 함께 사용하면 에이전트가 단순히 작업을 시작하는 것을 넘어 운영 상태를 설명하도록 구성할 수 있다.

## 시험 관점 정리

AWS 시험이나 아키텍처 문제에서는 다음 개념을 연결해서 기억할 수 있다.

- Step Functions는 여러 AWS 서비스와 작업을 상태 머신으로 오케스트레이션한다.
- AgentCore Gateway는 MCP를 통해 에이전트와 도구를 연결한다.
- 에이전트는 도구 선택을 담당하고 Step Functions는 정의된 업무 절차를 실행한다.
- Standard Workflows는 장시간 실행과 실행 기록이 중요한 업무에 적합하다.
- Express Workflows는 짧고 처리량이 높은 이벤트 기반 업무에 적합하다.
- 재시도와 오류 처리는 워크플로에 명시적으로 설계해야 한다.
- 영향이 큰 작업에는 최소 권한, 입력 검증, 사람의 승인, 감사 로그가 필요하다.
- 비동기 워크플로는 실행 시작과 결과 조회를 분리할 수 있다.

## 같이 보면 좋은 학습 포인트

- Amazon States Language와 Step Functions 상태 유형
- Standard Workflows와 Express Workflows 비교
- Step Functions의 Retry, Catch, Choice, Wait 상태
- Amazon Bedrock AgentCore Gateway와 MCP
- 에이전트 도구의 입력 스키마 설계
- Human-in-the-loop 승인 패턴
- 분산 트랜잭션의 Saga 및 보상 작업 패턴
- CloudTrail, CloudWatch, X-Ray를 이용한 워크플로 관측성

## 한 줄 정리

AgentCore Gateway를 통해 기존 Step Functions 워크플로를 AI 에이전트 도구로 연결하면서, 자연어 기반 판단과 정책에 따른 일관된 다단계 실행을 결합할 수 있게 되었다.
