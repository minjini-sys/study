# Amazon MSK Provisioned, 전송 중 데이터에 TLS 1.3 지원

## 공식 출처

- [Amazon MSK now supports TLS 1.3 for data in transit](https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-tls/)
- 발표일: 2026년 10월 30일

## 핵심 내용

Amazon Managed Streaming for Apache Kafka(Amazon MSK)가 MSK Provisioned 클러스터의 전송 중 데이터 암호화에 TLS 1.3을 지원한다.

TLS 1.3은 명명된 보안 정책(named security policy)을 클러스터 구성에서 선택하는 방식으로 적용한다. 각 보안 정책은 클러스터가 허용할 TLS 버전과 암호 스위트를 정의하며, 선택한 정책의 요구사항을 충족하지 못하는 연결은 거부된다.

AWS는 다음과 같은 단계적 전환 방식을 제공한다.

- TLS 1.2와 TLS 1.3을 함께 지원하는 정책: 클라이언트가 지원하는 가장 높은 TLS 버전으로 협상
- TLS 1.3 전용 정책: TLS 1.3 요구사항을 충족하는 연결만 허용

기존 MSK 클러스터에는 보안 정책을 직접 적용하기 전까지 변경이 발생하지 않는다. 이 기능은 MSK Provisioned를 지원하는 모든 AWS 리전에서 추가 기능 요금 없이 사용할 수 있다.

## 왜 중요한가

Kafka는 애플리케이션 이벤트, 로그, 결제 내역, 사용자 행동 데이터처럼 중요한 정보를 지속적으로 전달한다. 브로커와 프로듀서·컨슈머 사이의 통신을 최신 TLS로 보호하면 데이터 도청과 변조 위험을 줄이고 보안 표준을 강화할 수 있다.

TLS 1.3은 이전 버전보다 프로토콜을 단순화하고 오래된 암호화 방식을 제거하며, 연결 설정 과정의 보안과 효율을 개선한다. 또한 최신 규정 준수 프레임워크와 기업 보안 기준에서 TLS 1.3 요구가 늘고 있다.

AWS 발표에서는 TLS 1.3을 향후 포스트 양자 암호(PQC)를 적용하기 위한 전제 조건 중 하나로 설명한다. 지금 당장 모든 통신이 양자 내성을 갖는다는 의미는 아니지만, 현재 암호화된 트래픽을 수집해 미래에 해독하려는 위험에 대비하는 기반이 된다.

## 서비스 및 아키텍처 관점

MSK 보안 정책은 클러스터가 허용하는 TLS 버전과 암호 스위트의 경계를 정한다. 따라서 서버 쪽 설정만 변경하는 작업이 아니라 해당 클러스터에 연결하는 모든 클라이언트의 호환성을 함께 관리해야 한다.

안전한 전환 흐름은 다음과 같이 구성할 수 있다.

1. MSK 클러스터에 연결하는 프로듀서, 컨슈머, Kafka Connect 및 운영 도구를 조사한다.
2. 각 클라이언트의 런타임과 TLS 1.3 지원 여부를 확인한다.
3. 개발 및 스테이징 환경에서 TLS 1.2와 1.3을 함께 허용하는 정책을 적용한다.
4. TLS 1.3 지원 클라이언트가 실제로 TLS 1.3으로 협상하는지 검증한다.
5. 오래된 클라이언트와 라이브러리를 순차적으로 업그레이드한다.
6. 운영 환경에 호환 정책을 적용하고 연결 실패를 모니터링한다.
7. 모든 클라이언트 전환이 끝나면 보안 요구사항에 따라 TLS 1.3 전용 정책을 검토한다.

TLS 1.2와 1.3을 함께 허용하면 최신 클라이언트는 즉시 TLS 1.3을 사용하면서 기존 클라이언트는 TLS 1.2로 계속 연결할 수 있다. 이 방식은 전체 시스템을 한 번에 변경하지 않고 점진적으로 보안 수준을 높이는 데 유용하다.

## 보안 관점

- 보안 정책 변경 권한은 승인된 MSK 운영 역할에만 최소 권한으로 부여한다.
- TLS 정책은 전송 구간 암호화를 제어하며 인증과 권한 부여를 대신하지 않는다.
- IAM 액세스 제어, SASL/SCRAM 또는 상호 TLS 등 워크로드에 맞는 인증 방식도 함께 관리한다.
- 클러스터 보안 그룹과 네트워크 경로를 제한해 신뢰할 수 있는 클라이언트만 브로커에 접근하도록 한다.
- CloudTrail을 통해 클러스터 구성 및 보안 정책 변경 이력을 감사한다.
- TLS 1.3 전용 정책 적용 전 모든 클라이언트의 라이브러리, JDK, 운영 도구 호환성을 확인한다.
- 인증서 수명과 갱신 상태도 별도로 모니터링한다.

정책 요구사항을 충족하지 못하는 연결은 거부되므로, 보안 강화와 서비스 가용성을 함께 고려해야 한다. 충분한 검증 없이 엄격한 정책을 바로 적용하면 오래된 프로듀서나 컨슈머가 클러스터에 연결하지 못할 수 있다.

## 운영 관점

보안 정책 적용 전에는 클러스터별 연결 주체와 소유 팀을 목록화하는 것이 중요하다. Kafka 환경은 여러 팀과 애플리케이션이 공유하는 경우가 많아 한 개의 오래된 클라이언트가 전체 전환 일정을 늦출 수 있다.

운영 시에는 다음 항목을 관리한다.

- 클러스터별 현재 보안 정책
- 클라이언트 런타임과 TLS 1.3 지원 여부
- 브로커 연결 및 TLS 협상 실패 지표
- 프로듀서·컨슈머 재연결과 지연 시간 변화
- 정책 변경 전후의 처리량과 오류율
- 단계별 배포와 되돌리기 절차
- 규정 준수 기준이 요구하는 최소 TLS 버전과 암호 스위트
- 인프라 코드에서의 보안 정책 일관성

먼저 병행 지원 정책을 적용하고 관측 결과를 바탕으로 TLS 1.3 전용 정책으로 이동하는 방식이 운영 위험을 줄인다. 클라이언트 업그레이드가 끝났더라도 장애 대응 도구와 임시 운영 스크립트까지 확인해야 한다.

## 시험 관점 정리

AWS 시험이나 아키텍처 문제에서는 다음 개념을 연결해서 기억할 수 있다.

- Amazon MSK는 Apache Kafka 클러스터 운영을 관리형으로 제공한다.
- 이번 TLS 1.3 지원 대상은 MSK Provisioned 클러스터다.
- 명명된 보안 정책은 허용할 TLS 버전과 암호 스위트를 정의한다.
- 정책 요구사항을 충족하지 못하는 클라이언트 연결은 거부된다.
- TLS 1.2와 1.3 병행 정책은 단계적 마이그레이션에 적합하다.
- TLS 1.3 전용 정책은 더 엄격한 보안 및 규정 준수 요구에 사용할 수 있다.
- 전송 중 암호화, 저장 시 암호화, 인증, 권한 부여는 각각 구분해서 설계해야 한다.
- 기존 클러스터는 보안 정책을 적용하기 전까지 자동으로 변경되지 않는다.

## 같이 보면 좋은 학습 포인트

- TLS 1.2와 TLS 1.3의 주요 차이
- Amazon MSK의 전송 중 및 저장 시 암호화
- MSK의 IAM, SASL/SCRAM, 상호 TLS 인증
- Kafka 프로듀서와 컨슈머의 TLS 설정
- MSK 브로커와 클라이언트 연결 모니터링
- 보안 그룹과 VPC 기반 Kafka 네트워크 설계
- 포스트 양자 암호와 수집 후 해독 공격 개념
- CloudTrail을 이용한 MSK 구성 변경 감사

## 한 줄 정리

MSK Provisioned가 명명된 보안 정책을 통해 TLS 1.3을 지원하면서, 클라이언트 호환성을 유지한 점진적 전환과 TLS 1.3 전용 보안 강화를 선택할 수 있게 되었다.
