# AWS Security Hub, 컴퓨팅 리소스의 SBOM 인벤토리 제공

## 공식 출처

- [AWS Security Hub now provides an SBOM inventory for your compute resources](https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-sbom-inventory/)
- 발표일: 2026년 11월 6일

## 핵심 내용

AWS Security Hub가 컴퓨팅 리소스에 설치된 소프트웨어 패키지와 애플리케이션을 중앙에서 확인할 수 있는 Software Bill of Materials(SBOM) 인벤토리를 제공한다.

Security Hub는 Amazon Inspector가 다음 리소스에 대해 생성한 SBOM을 이용해 인벤토리를 구성한다.

- Amazon EC2 인스턴스
- Amazon ECR 컨테이너 이미지
- AWS Lambda 함수

SBOM 페이지에서는 패키지별 버전, 유형과 해당 패키지가 설치된 리소스 수를 볼 수 있다. 패키지 속성, AWS 계정과 리전을 기준으로 목록을 필터링하거나 그룹화할 수 있으며, 리소스 상세 페이지의 `Installed software` 탭에서는 특정 리소스에 설치된 전체 패키지를 확인할 수 있다.

인벤토리는 Security Hub API로도 조회할 수 있다. Security Hub Essentials에 추가 요금 없이 포함되며 Amazon Inspector가 활성화된 환경에서는 별도의 기능 활성화 없이 자동으로 채워진다.

## 왜 중요한가

보안 사고나 새 취약점이 공개되었을 때 가장 먼저 필요한 정보는 해당 소프트웨어가 조직의 어느 계정, 리전, 인스턴스, 컨테이너 이미지 또는 함수에 존재하는지다. 자산과 소프트웨어 구성을 중앙에서 파악하지 못하면 영향 범위 조사에 시간이 오래 걸리고 일부 리소스를 놓칠 수 있다.

조직 전체 SBOM 인벤토리를 사용하면 다음과 같은 질문에 빠르게 답할 수 있다.

- 특정 패키지와 버전이 어느 리소스에 설치되어 있는가?
- 취약한 구성 요소가 몇 개 계정과 리전에 퍼져 있는가?
- 하나의 리소스에는 어떤 소프트웨어 패키지가 포함되어 있는가?
- 보안 결과를 처리할 때 해당 패키지가 업무상 어떤 리소스에서 사용되는가?
- 패치 또는 이미지 재배포의 우선순위를 어디에 둘 것인가?

이는 취약점 대응뿐 아니라 소프트웨어 공급망 가시성, 라이선스 조사, 기술 부채 파악과 사용 중단 예정 패키지의 영향 분석에도 활용할 수 있다.

## 서비스 및 아키텍처 관점

이 기능에서 서비스별 역할은 다음처럼 나뉜다.

- Amazon Inspector: 컴퓨팅 리소스를 분석하고 SBOM과 취약점 정보를 생성
- AWS Security Hub: 여러 계정과 리전의 SBOM 데이터를 중앙 인벤토리로 제공
- Security Hub API: 자동 조사, 보고서 생성과 외부 보안 도구 연동에 사용

일반적인 활용 흐름은 다음과 같다.

1. 조직의 대상 계정과 리전에서 Amazon Inspector를 활성화한다.
2. Inspector가 EC2, ECR 이미지와 Lambda 함수의 소프트웨어 구성을 분석한다.
3. Security Hub가 생성된 SBOM을 자동으로 인벤토리에 반영한다.
4. 보안 팀이 패키지 이름, 버전, 계정 또는 리전으로 검색한다.
5. 영향을 받는 리소스와 업무 중요도를 확인한다.
6. 패치, 컨테이너 이미지 재빌드 또는 Lambda 재배포를 담당 팀에 요청한다.
7. 변경 후 인벤토리와 Inspector 결과에서 수정 여부를 다시 확인한다.

SBOM 인벤토리는 무엇이 설치되어 있는지를 보여주는 자산 정보다. 특정 패키지가 실제 취약한지, 공격 가능성이 높은지와 수정 우선순위는 Inspector 결과, 취약점 심각도, 네트워크 노출과 리소스 중요도를 함께 검토해 판단해야 한다.

## 보안 관점

- 조직 전체 계정과 사용 리전에서 Inspector와 Security Hub 활성화 범위를 점검한다.
- Security Hub의 위임 관리자와 중앙 구성으로 계정별 설정 편차를 줄인다.
- SBOM 조회 권한은 보안 담당자와 승인된 자동화 역할에 최소 권한으로 부여한다.
- 소프트웨어 목록은 내부 기술 스택과 버전을 드러내므로 인벤토리 API 접근과 내보낸 보고서를 보호한다.
- 패키지 버전만으로 위험을 판단하지 말고 Inspector 결과와 리소스 노출 정보를 함께 사용한다.
- ECR 이미지에서 문제가 발견되면 실행 중 컨테이너뿐 아니라 동일 이미지를 사용하는 배포 파이프라인도 확인한다.
- CloudTrail을 이용해 Security Hub 설정과 인벤토리 API 사용을 감사한다.

SBOM은 구성 요소 가시성을 제공하지만 악성 행위 탐지, 구성 오류 검사 또는 런타임 보호를 모두 대신하지 않는다. GuardDuty, Security Hub CSPM, Inspector와 애플리케이션 보안 테스트를 함께 사용하는 다층 방어가 필요하다.

## 운영 관점

인벤토리의 품질은 Amazon Inspector가 실제로 활성화되어 있고 대상 리소스를 분석할 수 있는지에 달려 있다. 따라서 단순히 Security Hub 화면이 열리는지만 확인하지 말고 계정, 리전과 리소스 유형별 데이터 범위를 점검해야 한다.

운영 시에는 다음 항목을 관리한다.

- Inspector와 Security Hub가 활성화된 계정 및 리전
- EC2, ECR 이미지, Lambda 함수별 인벤토리 포함 범위
- 패키지 이름과 버전을 기준으로 한 정기 검색
- 새 고위험 취약점 발표 시 영향 범위 조사 절차
- 리소스 소유자, 환경과 업무 중요도를 연결하는 태그
- 패치 후 이전 버전이 인벤토리에서 사라졌는지 확인
- 오래된 ECR 이미지와 사용하지 않는 Lambda 버전 정리
- API를 이용한 정기 보고서와 티켓 자동 생성

같은 패키지가 수많은 리소스에 설치되어 있어도 모든 리소스의 위험도가 같지는 않다. 인터넷 노출, 실행 여부, 데이터 민감도, 대체 가능성과 업무 중요도를 기준으로 대응 순서를 정해야 한다.

## 시험 관점 정리

AWS 시험이나 아키텍처 문제에서는 다음 개념을 연결해서 기억할 수 있다.

- SBOM은 소프트웨어에 포함된 구성 요소와 버전의 목록이다.
- Amazon Inspector는 EC2, ECR 이미지와 Lambda의 소프트웨어 취약점을 평가한다.
- Security Hub는 여러 보안 서비스의 결과와 보안 상태를 중앙에서 관리한다.
- 이번 SBOM 인벤토리는 Inspector가 생성한 데이터를 사용한다.
- 패키지 속성, 계정과 리전으로 인벤토리를 필터링하고 그룹화할 수 있다.
- 리소스 상세 화면에서 설치된 전체 소프트웨어를 확인할 수 있다.
- 인벤토리와 취약점 결과는 목적이 다르며 함께 분석해야 한다.
- Organizations와 위임 관리자를 이용하면 멀티 계정 보안 운영을 중앙화할 수 있다.

## 같이 보면 좋은 학습 포인트

- SBOM과 소프트웨어 공급망 보안
- Amazon Inspector의 EC2, ECR, Lambda 및 AMI 스캔
- AWS Security Hub Essentials와 CSPM
- Security Hub 중앙 구성 및 위임 관리자
- ECR 이미지 재빌드와 컨테이너 패치 전략
- Lambda 함수 코드 및 계층의 의존성 관리
- CVE, CVSS와 위험 기반 취약점 우선순위
- Security Hub API를 이용한 자동 대응

## 한 줄 정리

AWS Security Hub의 SBOM 인벤토리는 Inspector가 분석한 EC2, ECR 이미지와 Lambda의 소프트웨어 구성 요소를 조직 전체에서 중앙 조회하게 해 취약점 영향 범위와 패치 우선순위를 더 빠르게 파악할 수 있게 한다.
