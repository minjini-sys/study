# AWS Emulator 정식 출시, AWS 애플리케이션을 로컬에서 테스트

## 공식 출처

- [AWS Emulator is now available for building and testing AWS applications locally](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-emulator-now-available/)
- [Test your applications against AWS locally with AWS Emulator](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/)
- 발표일: 2026년 11월 11일

## 핵심 내용

AWS가 AWS 애플리케이션을 개발자 컴퓨터나 CI 환경에서 로컬로 구축하고 테스트할 수 있는 AWS Emulator를 정식 출시했다. 기존 AWS SDK와 AWS CLI가 클라우드 대신 로컬 HTTPS 엔드포인트를 호출하도록 환경을 설정하며, 애플리케이션 코드는 그대로 유지할 수 있다.

주요 특징은 다음과 같다.

- AWS 계정이나 클라우드 배포 없이 지원되는 AWS API를 로컬에서 호출할 수 있다.
- AWS SDK와 AWS CLI에서 사용하는 것과 같은 API 형태를 제공한다.
- 지원되는 작업은 유효한 요청의 결과와 잘못된 요청의 오류를 AWS와 동일하게 재현하는 것을 목표로 한다.
- 아직 구현되지 않은 작업은 HTTP 501 Not Implemented를 반환한다.
- 각 실행 인스턴스가 자체 포트, 키와 메모리 상태를 사용해 테스트와 CI 작업을 서로 격리한다.
- 로컬 프로세스 또는 컨테이너로 실행할 수 있고 Rust SDK에서는 테스트 프로세스에 포함하는 임베디드 모드도 제공한다.
- Linux에서는 RPM 또는 Debian 패키지로 설치하며 macOS와 Windows에서는 Docker로 실행할 수 있다.
- 추가 서비스 요금이 없고 소스 코드가 공개돼 있다.

## 왜 중요한가

AWS API를 사용하는 코드를 확인하려면 개발 계정에 리소스를 배포하고 결과를 기다리는 과정이 반복된다. 이 과정은 피드백 속도를 늦추고 테스트 비용과 리소스 정리 부담을 만든다. 여러 테스트나 코딩 에이전트가 같은 계정을 공유하면 리소스 이름 충돌과 상태 간섭도 발생할 수 있다.

AWS Emulator는 DynamoDB 테이블 생성, S3 객체 처리 같은 지원 API 흐름을 밀리초 단위의 로컬 반복 과정으로 옮긴다. 개발자와 코딩 에이전트가 오류를 더 빨리 발견하고, CI 작업마다 독립된 상태에서 동일한 테스트를 병렬 실행할 수 있다. 다만 로컬 테스트는 실제 AWS 통합 테스트를 대체하지 않으며 배포 전 피드백 단계 하나를 추가하는 도구로 봐야 한다.

## 서비스 및 아키텍처 관점

AWS Emulator를 시작하면 자체 자격 증명, 구성 파일과 인증서를 생성하고 기본적으로 로컬 HTTPS 엔드포인트를 제공한다. 환경 변수를 통해 SDK와 CLI의 엔드포인트 및 자격 증명 경로를 Emulator 쪽으로 전환한다.

일반적인 개발 흐름은 다음과 같다.

1. 개발자 PC나 CI 실행 환경에서 AWS Emulator를 시작한다.
2. 실제 AWS 자격 증명을 제거하고 Emulator가 생성한 키와 로컬 엔드포인트를 설정한다.
3. 기존 AWS SDK, CLI 또는 애플리케이션 테스트를 실행한다.
4. 지원되지 않는 API와 AWS 동작 차이는 fidelity report로 확인한다.
5. 로컬 테스트를 통과한 결과물을 별도 AWS 테스트 계정에 배포한다.
6. IAM, 네트워크, 교차 계정과 리전 동작을 포함한 실제 통합 테스트를 수행한다.

Emulator의 리소스 상태는 메모리에 저장돼 프로세스를 종료하면 사라진다. 각 실행이 독립된 상태를 가지므로 테스트 격리는 쉬워지지만, 재시작과 장기 지속성에 의존하는 시나리오는 실제 환경에서 별도로 검증해야 한다.

## 보안 관점

- AWS Emulator는 IAM 정책과 리소스 기반 정책을 실제 AWS와 같은 방식으로 평가하지 않는다.
- 실제 AWS에서 거부될 요청이 Emulator에서는 성공할 수 있으므로 보안 권한 테스트 도구로 사용하면 안 된다.
- 테스트 셸과 CI 환경에서 실제 AWS 액세스 키, 세션 토큰과 프로파일을 제거한다.
- Emulator가 생성한 전용 자격 증명만 사용하고 엔드포인트가 로컬인지 확인한다.
- 기본적으로 로컬 컴퓨터에서만 수신하도록 유지하고 불필요하게 외부 네트워크에 노출하지 않는다.
- 실제 AWS 배포 전 IAM 최소 권한, 리소스 정책, 암호화와 네트워크 제어를 별도 검증한다.
- 테스트 데이터에도 민감 정보나 운영 자격 증명을 넣지 않는다.

로컬 에뮬레이션의 편리함 때문에 보안 검증 단계를 생략하면 환경 차이로 인한 권한 문제가 운영에 남을 수 있다. Emulator 테스트와 AWS 테스트 계정을 이용한 보안 검증을 파이프라인의 서로 다른 단계로 유지해야 한다.

## 운영 관점

AWS는 서비스별 동작 일치 수준을 fidelity test와 fidelity report로 공개한다. 테스트가 통과했다는 사실만 보지 말고 사용하는 서비스와 API의 현재 지원 범위를 확인해야 한다.

운영 시에는 다음 항목을 관리한다.

- 테스트가 호출하는 API의 구현 여부와 fidelity 점수
- HTTP 501 Not Implemented 응답을 명확한 테스트 실패로 처리하는지 여부
- Emulator 버전 고정 및 업데이트 주기
- CI 작업별 독립 포트, 키와 상태 분리
- 로컬 인증서 신뢰 설정과 SigV4 요청 서명
- 실제 AWS 자격 증명이 테스트 환경에 섞이지 않도록 하는 검사
- 로컬 테스트와 실제 AWS 통합 테스트의 책임 범위
- Emulator와 실제 AWS에서 발생하는 결과 및 오류 차이

로컬 테스트가 빨라져도 운영 전 테스트 계정의 검증을 없애서는 안 된다. API 동작, IAM 권한, 서비스 할당량, 리전별 기능, 성능과 장애 조건은 실제 AWS 환경에서 확인해야 한다.

## 시험 관점 정리

AWS 시험이나 아키텍처 문제에서는 다음 개념을 연결해서 기억할 수 있다.

- AWS Emulator는 AWS SDK와 CLI의 호출을 로컬 HTTPS 엔드포인트에서 처리한다.
- 지원되는 API를 AWS 계정이나 리소스 배포 없이 개발·테스트할 수 있다.
- 각 Emulator 인스턴스는 자체 포트, 키와 인메모리 상태를 가진다.
- 구현되지 않은 작업은 501 Not Implemented를 반환한다.
- Emulator는 IAM과 리소스 기반 정책을 실제 AWS와 동일하게 평가하지 않는다.
- 교차 계정 및 교차 리전 동작을 재현하지 않으며 하나의 계정처럼 동작한다.
- 로컬 테스트는 빠른 피드백을 위한 것이고 실제 AWS 통합·보안 테스트를 대체하지 않는다.
- 추가 서비스 요금은 없지만 실제 AWS에 배포한 리소스에는 정상 요금이 적용된다.

## 같이 보면 좋은 학습 포인트

- AWS SDK 엔드포인트 재정의
- AWS Signature Version 4 요청 서명
- 단위 테스트, 통합 테스트와 엔드투엔드 테스트의 차이
- CI 작업 격리와 테스트 상태 관리
- IAM 정책 평가 로직
- 다중 계정 개발·테스트 환경 설계
- Infrastructure as Code 테스트 전략
- 서비스별 fidelity report 읽는 방법

## 한 줄 정리

AWS Emulator는 기존 AWS SDK와 CLI 호출을 독립된 로컬 환경에서 빠르게 시험하게 해주지만 IAM과 실제 클라우드 동작을 완전히 재현하지 않으므로 AWS 통합 테스트와 함께 사용해야 한다.
