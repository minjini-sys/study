# Amazon Bedrock AgentCore로 만드는 자가 복구 ETL 파이프라인

## 공식 출처

- [Build a self-healing ETL pipeline with Amazon Bedrock AgentCore](https://aws.amazon.com/blogs/big-data/build-a-self-healing-etl-pipeline-with-amazon-bedrock-agentcore/)
- 게시일: 2026년 11월 13일

## 핵심 내용

AWS Big Data Blog가 AWS Glue와 Amazon Bedrock AgentCore를 결합해 데이터 오류를 탐지하고 수정하는 자가 복구 ETL 참조 아키텍처를 공개했다. 이 구조는 잘못된 레코드를 고쳐 데이터 레이크에 다시 저장하며, 선택적으로 오류의 근본 원인을 해결하는 코드 변경을 Pull Request로 제안한다.

핵심 구성은 다음과 같다.

- AWS Glue ETL 작업이 레코드를 스키마에 따라 검증하는 품질 게이트 역할을 한다.
- 정상 레코드는 변환 영역으로 보내고 실패 레코드는 오류 유형과 세부 정보를 포함해 AgentCore로 전달한다.
- 오케스트레이터, 데이터 수정, 데이터 저장, 코드 개선의 네 가지 전문 에이전트가 순서대로 작업한다.
- Amazon Bedrock Knowledge Bases가 도메인 문서에서 새로운 오류의 수정 방법을 검색한다.
- Amazon S3 Vectors에 저장된 사전 계산 수정 전략이 알려진 오류를 빠르게 처리한다.
- 두 지식 소스 중 신뢰도가 높은 전략을 선택하고 기준값을 넘을 때만 자동 조치한다.
- 신뢰도가 부족하면 Amazon SNS로 사람에게 검토를 요청한다.
- 저장소 자격 증명을 설정한 경우 코드 개선 에이전트가 원인 분석과 수정안을 담은 Pull Request를 생성할 수 있다.

이 글은 신제품 출시 공지가 아니라 AWS가 공개한 고급 참조 구현과 운영 패턴이다. 실제 환경에서는 조직의 데이터 특성과 위험 허용 수준에 맞춰 검증 로직, 신뢰도 기준과 승인 절차를 다시 설계해야 한다.

## 왜 중요한가

ETL 파이프라인에서는 스키마 변경, 누락 필드, 자료형 불일치와 생산자 버그가 데이터 품질 문제를 만든다. 일반적으로 오류 레코드는 Dead Letter Queue 등에 쌓이고 엔지니어가 탐지, 분석, 수정, 재처리와 코드 배포를 반복한다. 데이터 종류와 양이 늘수록 이 수동 과정은 처리 지연과 운영 부담을 키운다.

자가 복구 구조는 이미 검증된 수정 지식을 재사용하고, 불확실한 상황만 사람에게 전달한다. 레코드를 고치는 데서 끝나지 않고 원인 코드의 수정안까지 제안해 같은 오류의 반복을 줄인다는 점도 중요하다. 다만 자동 수정이 잘못된 데이터를 정상으로 오인하게 만들 수 있으므로 원본 보존, 설명 가능성, 가역성과 사람의 감독이 반드시 필요하다.

## 서비스 및 아키텍처 관점

참조 아키텍처의 데이터 흐름은 다음과 같다.

1. 데이터 생산자가 원본 레코드를 Amazon S3 원시 영역에 저장한다.
2. AWS Glue가 레코드를 스키마별로 검증한다.
3. 정상 레코드는 변환 영역에 저장되고 오류 레코드는 AgentCore 오케스트레이터에 전달된다.
4. 데이터 수정 에이전트가 Bedrock Knowledge Base와 사전 계산된 S3 수정 전략을 조회한다.
5. 신뢰도가 기준 이상이면 수정 전략을 적용하고 저장 에이전트가 결과를 데이터 레이크에 기록한다.
6. 코드 개선 에이전트가 상류 코드의 원인을 분석하고 선택적으로 Pull Request를 제안한다.
7. 신뢰도가 부족하거나 단계가 실패하면 자동 처리를 멈추고 SNS로 사람에게 알린다.

전문 에이전트별로 책임을 분리하면 수정 전략, 저장 대상과 저장소 연동을 독립적으로 바꿀 수 있다. 원본, 변환, 수정 영역을 분리하면 감사와 재처리가 쉬워지고 소비자는 검증된 데이터와 수정된 데이터를 함께 사용할 수 있다.

## 보안 관점

- 각 AgentCore Runtime과 Glue 작업 역할에는 필요한 S3 경로, 모델, 지식 기반과 알림 권한만 부여한다.
- 저장소 토큰은 AWS Secrets Manager에 보관하고 코드 개선 기능이 필요하지 않으면 자격 증명을 제공하지 않는다.
- 에이전트가 생성한 코드 변경은 자동 병합하지 않고 사람의 리뷰와 CI 검증을 거치도록 한다.
- 원본 레코드는 변경하지 않고 별도 영역에 보존해 자동 수정 결과를 추적하고 되돌릴 수 있게 한다.
- 민감 데이터가 모델 입력, 로그, 지식 기반과 Pull Request에 노출되지 않도록 마스킹과 접근 제어를 적용한다.
- 신뢰도 점수만으로 안전성을 판단하지 말고 허용된 수정 유형과 필드 범위를 정책으로 제한한다.
- Amazon Bedrock Guardrails, 콘텐츠 필터링과 근거 확인을 추가적인 통제로 검토한다.
- CloudTrail과 CloudWatch Logs로 에이전트 호출, 비밀 접근, S3 쓰기와 코드 변경 활동을 감사한다.

에이전트가 데이터와 코드를 모두 수정할 수 있는 구조는 영향 범위가 크다. 데이터 수정 권한과 저장소 쓰기 권한을 분리하고, 위험한 작업에는 명시적인 승인 단계를 두는 것이 중요하다.

## 운영 관점

운영 시에는 다음 항목을 관찰한다.

- 스키마 유형별 검증 실패율과 오류 유형 분포
- 자동 수정 성공률, 평균 신뢰도와 사람 검토 전환율
- 수정 전후 레코드의 차이와 재검증 결과
- 잘못된 자동 수정의 비율과 탐지 시간
- AgentCore 호출 지연, 모델 오류와 비용
- Knowledge Base 검색 품질과 S3 수정 전략의 버전
- SNS 알림 전달과 담당자의 처리 시간
- 생성된 Pull Request의 승인률, 실패율과 동일 오류 재발률
- 수정 레코드가 하류 분석과 모델에 미치는 영향

신뢰도 기준은 오류 유형별 위험에 따라 다르게 설정하는 것이 좋다. 단순한 단위 변환처럼 결정적인 수정은 자동화할 수 있지만, 의미 해석이 필요한 값은 사람 검토로 보내는 방식이 안전하다. 새로운 수정 전략은 과거 오류 데이터로 평가한 후 단계적으로 적용해야 한다.

## 시험 관점 정리

AWS 시험이나 아키텍처 문제에서는 다음 개념을 연결해서 기억할 수 있다.

- AWS Glue는 서버리스 데이터 통합 및 ETL 서비스로 데이터 검증과 변환을 수행할 수 있다.
- Amazon Bedrock AgentCore는 AI 에이전트를 배포하고 운영하기 위한 관리형 기능을 제공한다.
- Bedrock Knowledge Bases는 도메인 문서를 기반으로 RAG 검색을 제공한다.
- S3 Vectors는 알려진 패턴에 대한 벡터 검색과 사전 계산 전략 저장에 활용할 수 있다.
- 전문 에이전트 분리는 오케스트레이션, 수정, 저장과 코드 개선의 책임을 나눈다.
- 신뢰도 기준 미달 시 SNS로 사람에게 넘기는 흐름은 안전한 실패와 Human-in-the-loop 패턴이다.
- 원본 데이터를 보존하고 수정 영역을 분리하면 감사, 재현과 롤백이 쉬워진다.
- Secrets Manager는 저장소 토큰 같은 비밀 정보를 코드와 분리해 관리한다.

## 한 줄 정리

AWS Glue와 Amazon Bedrock AgentCore를 결합한 자가 복구 ETL 패턴은 데이터 오류를 자동 수정하고 재발 방지 코드까지 제안하되, 낮은 신뢰도의 작업은 사람에게 넘겨 안전한 자동화 폐루프를 만든다.
